# RatMath / RiX review, 2026-10-08

A first deep dive across the umbrella repository: the RiX language (main focus),
core rational arithmetic, RiX Web and its tutorials, the legacy calculators, and
the RiX notebook. No source was changed. Everything under "verified" was run and
observed at these revisions: umbrella `d2b86f2`, `rix` `d525695`, core `v0.6.0`.
Items marked *inferred* come from reading code only.

## Status after the same-day fixes

The following findings were fixed later on 2026-10-08 (uncommitted working-tree
changes in `rix`, `packages/core`, `rix-web` and `rix-nb` at the time of
writing). The sections below describe the state before those fixes.

- Comparisons chain (`0 < 5 < 3` is null, each operand evaluated once); mixing
  `<` and `>` in one chain is an error. A single comparison still returns `1`.
- A space is ordinary multiplication (`a/b c` is `(a/b)*c`, `1/2 ~[m]` is half
  a metre); no space forms one tight term (`1/2x` is `1/(2x)`). Fractional
  magnitudes print with the space. Lint RX1709 flags the unspaced form.
- `==` compares arrays, tuples, sets and maps by value. Ordering with null is
  null; ordering across types is an error.
- An explicit element count lifts the 10,000 sequence limit.
- Pipe, range, sort and concatenation results are mutable.
- String literals that are only punctuation are no longer read as punctuation
  (this was the cause of `Join(",")`).
- `k m (m + 1)` multiplies. Lint RX1708 flags a pipe after a lambda body.
- Core `pow` uses native exponentiation. The notebook keeps a leading quote.

Still open: recursion depth, error-message quality, block versus function
scoping, the core `Integer`/`Rational` comparison and string constructor,
RiX Web main-thread evaluation, the notebook async budget and export findings,
and the documentation drift in section 6.

## Summary

The exact arithmetic is sound. In roughly 250 RiX expressions and the core
probes, I found no wrong sum, product, quotient, or interval enclosure. The test
suites are large and green. The problems are almost all at the edges of the
language surface: a handful of expressions that parse and silently return a
wrong or surprising answer, some low default limits, and documentation that has
drifted from the implementation.

The five things I would fix first:

1. Chained comparisons silently give wrong answers (`0 < 5 < 3` is true).
2. `1/2~[m]` and `3/2~{pi}` mean 1/(2 m) and 3/(2π); two tutorial cells fall
   into this themselves.
3. `==` on arrays, sets, tuples and maps compares identity, not value, and
   mixed-type `<` returns arbitrary answers instead of an error.
4. Finite sequences longer than 10,000 elements cannot be summed or measured,
   and recursion by name overflows the JavaScript stack at a few thousand frames.
5. The legacy CLI calculator cannot display `1/97`, and strips spaces so `3 4`
   becomes `34`.

## 1. RiX language

### 1.1 Silent wrong or surprising results (verified)

These matter most because nothing tells the user anything went wrong. `rix lint`
at `--level=pedantic --profile=all` reports no diagnostics for any of them.

| Input | Result | Comment |
|---|---|---|
| `0 < 5 < 3` | `1` | Comparisons are left-associative: `(0 < 5) < 3` is `1 < 3`. |
| `1 < 2 < 2` | `1` | Same cause. |
| `3 > 2 > 1` | `_` | Same cause; a true statement comes out false. |
| `1/2~[m]` | `1/2~[1/m]` | Unit sugar binds tighter than `/`. |
| `3/2~{pi} == 3/2 * .Exact[:pi]` | `_` | Same; the left side is 3/(2π). |
| `1:2 + 1:2` | `_` | `:` binds looser than `+`, so this is the betweenness test `1:3:2`. |
| `1:2 * 2`, `2 * 1:2` | `1:4`, `2:2` | Same precedence; neither is the scaled interval `2:4`. |
| `[1,2] == [1,2]` | `_` | Falls through to JavaScript `===`. |
| `{\| 1,2 \|} == {\| 2,1 \|}` | `_` | Same for sets, tuples and maps. |
| `5 < "abc"` / `"abc" < 5` | `1` / `_` | JavaScript coercion leaks through. |
| `_ < 1`, `1 > _` | `1`, `1` | Null orders below numbers. |
| `"1" + 1` | `11` | String concatenation by coercion. |
| `x := 5; x.Foo`, `m.b`, `[1,2,3][0]`, `[1,2,3][4]` | `_` | Misses are silent. |
| `a := [1,2,3]; a[5] ~= 9` | `[1, 2, 3, , 9]` | Out-of-range write extends with a hole. |

Details and suggestions:

- **Chained comparisons.** A mathematical language should either chain them
  (`a < b < c` meaning both hold) or reject them at parse time. Nothing in the
  introduction, syntax guide or rationales mentions the current behaviour.
  Precedence is at `rix/src/parser/parser.js:23-24`.
- **Unit and generator sugar.** `1/2~[m]` reading as half a metre is the natural
  reading, and `rix-web/tutorials/exact-generators.md:19-22` and `:58-60` are
  written on that assumption. The first cell's prose says the two forms are the
  same; the cell returns `_`. `halfTurn := 1/2~{pi}~[rad]` evaluates to
  `1/2~{pi^-1}~[1/rad]`. Either make `~[...]`/`~{...}` bind looser than `/`
  when the left side is a numeric literal fraction, or add a lint rule.
- **Interval colon.** The precedence is a deliberate design (it is what lets
  `1/2:3/4` work), but `1:2 + 1:2` silently yielding "false" is a trap. A lint
  rule for "interval literal used as an arithmetic operand without parentheses"
  would cover it.
- **Collection equality.** The introduction describes `==` as value equality
  (`rix/documentation/introduction.md:479`). For collections, `EQ` reaches
  `boolResult(a === b)` at `rix/src/eval/functions/comparison.js:258`, so only
  the same object is equal. Sets that differ only in order being unequal is
  the most surprising case.
- **Mixed-type ordering.** `LT`/`GT` fall back to JavaScript `<` on arbitrary
  values (`comparison.js:158-163`). `.Min(3, "a")` already errors correctly with
  "COMPARE requires two values from the same built-in ordered domain"; the
  operators should do the same.

Three more, reported by the Project Euler work and reproduced here:

- `[1, 2].Join(",")` returns `1[object Object]2`. `Join(" ")` and `Join(", ")`
  work, so a separator consisting of a single comma is being treated as
  something other than a string.
- `k m (m + 1)` fails with "Expression is not callable", while `n(n+1)` and
  `k*m(m + 1)` multiply. Three-way juxtaposition with a parenthesised factor is
  not handled.
- The result of a pipe cannot be index-assigned:
  `a := [1,2,3] |>> (x -> x); a[1] ~= 9` fails with "collection is not mutable"
  until `a._mutable = 1` is set. `introduction.md:1015` says arrays are
  structurally mutable by default.

The same thread reported that a chain ending in an unparenthesised reducer
lambda fails with "PREDUCE requires a collection". The simple form
`xs |>> ((i) -> i^2) |>: (a, b) -> a + b` works here; the failure I can
reproduce is the lambda-body case in 1.3. It also reported that the notebook's
result list drops the leading quote of a statement that begins with a string
literal; I did not verify that one.

### 1.2 Limits that are low for real work (verified)

- **Finite sequences over 10,000 elements cannot be consumed.**
  `[1, |+ 1, |; 50000] |>: @+[2]` and `.Len(...)` of the same fail with
  "Async lazy cache limit of 10000 exceeded". 9,000 elements work. The message
  says "Async" although nothing asynchronous is involved, and I found no
  documented way to raise the limit (`rix/src/runtime/lazy-sequence.js:34`).
- **Loops stop at 10,000 iterations by default.** This is documented and
  `{@::@ ... }` lifts it, but the error message does not mention that form.
- **Recursion depth.** `F(n) -> n == 0 ?: 0 ?_ 1 + F(n-1)` works at 2,500 and
  fails at 5,000 with a raw "Maximum call stack size exceeded". Tail calls are
  only optimised when written with `$`: `F(n-1, acc+n)` in tail position
  overflows at 100,000 where `$(n-1, acc+n)` succeeds. Mutual recursion
  (`Even`/`Odd`) overflows at 20,000. A depth counter with a RiX-level error
  that names `$` would be a cheap improvement.
- **Big powers.** `2^524288` fails with "Out of memory: BigInt generated from
  this operation is too big", while native `2n ** 1000000n` takes a millisecond.
  The cause is in core (section 2, item 3).

These four will be the first walls anyone hits doing Project Euler style work.

### 1.3 Error messages and diagnostics (verified)

Generally good: parse errors carry line and column, the RX1001 scope hint is
excellent, and the "name must be Capitalised" message for `f(3)` is exactly
right. Weak spots:

- `4^(1/2)` gives "Exponent must be a safe integer; use a string or bigint for
  exact values", a JavaScript API message. It should say fractional exponents
  need a real-number plugin.
- `1 + _`, `[1,2] + [3,4]`, `[1,2] * 2` all give "Cannot use object in
  arithmetic" without naming the type.
- `1e3` gives "Undefined variable: e3". Scientific notation is `1_^3` by design;
  a targeted hint would help everyone arriving from another language.
- `.Sqrt(2)`, `.Gcd(12,18)`, `.Sum(...)` give "Unknown system capability" with no
  suggestion of which plugin provides it or a near-match.
- Runtime errors inside a function report only the innermost location, with no
  call site.
- `x -> x |> f` parses as `(x -> x) |> f`, so a pipe inside an unparenthesised
  lambda body fails with "PREDUCE requires a collection".
- `a |>> (x -> a[1] ~= 0)` gives "Invalid update target" with no location.
- `Nonzero(0)` reports "NONZERO prep failed": the user's name is upper-cased.

### 1.4 Scoping is inconsistent between blocks and functions (verified)

`x := 10; {; x + 1 }` fails and asks for `@x`. But `F() -> x + 1` reads the
outer `x` with no `@`, and `Bump() -> {; total += 1 }` even mutates it. A
learner is told blocks are for grouping, then finds a bare block is stricter
than a function. The block tutorials (`control.md`, `brace-containers.md`) never
mention the `@` requirement, and `scope.md` presents `@` as how functions read
outer names although it is optional there.

### 1.5 Display

- Decimal input comes back as mixed fractions: `1.23[56:67]` prints
  `1..589/2500:1..2367/10000`. The at-a-glance page annotates it as
  `1.2356:1.2367`. A "display like the input" default for decimal literals would
  make the calculator much friendlier.
- `5:2` prints as `5:2` but behaves as `2:5` in arithmetic.
- `(2/3).ToDecimal(3)` gives `0.666`: truncated, not rounded, and with no marker
  that it is inexact, unlike `ToDecimalApproximation` which adds `?`.

### 1.6 Comprehensiveness

- The surface is very large: about 70,000 lines of JavaScript in `rix/src`,
  38,000 lines of RiX and 16,000 of JavaScript across 64 plugins, and 53,000
  lines of tests, built in 381 commits since July. The core language traps in
  1.1 are small next to that, which is an argument for a short hardening pass on
  the core before adding more plugins.
- With `--plugins=none` the 400-odd system functions include `AUDIO`,
  `HTTPSTREAM`, `FIGURE` and a dozen `CALCULUS...` entries, but no gcd, integer
  square root, primality test, sum or range. For a rational calculator those are
  the expected basics.
- `evaluator.js` carries a synchronous evaluator (from line 1234) and a separate
  asynchronous one (roughly lines 1450-4950). The notebook finding in section 5
  (examples pass on sync, fail on async) is the kind of divergence that
  structure invites. *Inferred:* this is the main long-term maintenance risk.
- There is no `-e 'expr'` flag; `rix -e 1` tries to open a file named `-e`.
- A script header `plugins: [full]` fails with "Unknown plugin 'full'" although
  `--plugins=full` works.

### 1.7 Good

Exact arithmetic, repeating decimals, mixed numbers, bases, units with dimension
checking, certified `?` values with three-state comparison, cells and the five
assignment forms, closures, multifunctions with prep guards, and the pipe family
all behaved as documented. Performance is reasonable for a tree-walking
interpreter: 200,000 loop iterations in about 0.4 s, `Fib(24)` in about 0.25 s,
0.4 s startup bare and 0.75 s with the full plugin set.

## 2. Core rational arithmetic (`packages/core`)

Arithmetic, normalisation, interval multiply/divide/power, continued fractions,
repeating decimals and base output were correct in everything probed, including
7,260 round trips and about 29,000 best-approximation cases against brute force.

Verified bugs:

1. **Integer compared with Rational is silently wrong.**
   `new Integer(3).compareTo(new Rational(7,2))` returns `0`;
   `new Integer(5).equals(new Rational(5))` returns `false`; the reverse
   direction, `new Rational(1,2).lessThan(new Integer(3))`, throws "Invalid mix
   of BigInt and other type". `integer.js:249-298` reads `other.value`, which a
   Rational does not have. RiX is not affected (it has its own comparison), but
   any direct user of the published package is.
2. **`Rational.toNumber()` returns `NaN` for large operands**, for example
   `(10^400 + 1) / 10^400` (`rational.js:969`).
3. **`pow` performs one wasted final squaring** (`integer.js:233-239`,
   `rational.js:548-555`), which is the most expensive step and is what makes
   `2^524288` run out of memory. Using native `**` fixes both speed and limit.
4. **The Rational string constructor accepts garbage**: `""`, `"."`, `"/2"` all
   become `0`, and `new Rational("3/4", 5)` ignores the 5. `number-parser.js` is
   strict and correct; the constructor should delegate to it.
5. **`compactedDecimalInterval()` and `relativeMidDecimalInterval()` can print
   text that does not enclose the interval** for non-terminating endpoints.
   `1/3:2/3` prints an upper bound truncated inward.

Design notes: `equals`/`contains` throw raw TypeErrors on other types; type
dispatch uses `constructor.name === "Integer"`, which breaks under minification;
`Rational.zero` and `one` are writable; `Integer.modulo` is truncated with no
floored variant; gcd is plain Euclid on every construction.

Secondary packages are in worse shape than core:

- `packages/arith-funs/src/core-arith.js` calls `Rational.compare`, `.ceiling`
  and `.truncate`, none of which exist, so `Cmp`, `Eq`, `Lt`, `Ceil` and `Trunc`
  throw when called.
- `packages/reals` falls back to `Math.exp`/`Math.log` and returns intervals
  that do not contain the true value (`EXP(1,-15)` is off by about 5e-8 with a
  stated width of 2e-9). For a library whose premise is certified enclosures,
  this is the most serious correctness problem in the legacy packages.

## 3. RiX Web and tutorials

All 406 fenced cells in the 90 core tutorials run without error under the
default browser profile, and 47 stated outputs in early and middle lessons
matched. The beginner route is well sequenced and lesson 1 is well built.

Verified problems:

1. The two `exact-generators.md` cells described in 1.1.
2. `control-panels.md:478-492`: the challenge starter redeclares `$$view` from
   its own section and fails with "Reactive declaration requires a new name".
3. The tutorial execution test (`tests/repl-runtime.test.js:1130-1150`) asserts
   only that a result came back, not what it was, skips indented challenge
   starters, and is not in `test:short`. That is why 1 and 2 went unnoticed.
   `tutorial-improvement-plan.md` is marked "implemented" while its acceptance
   box for exactly this check is unticked.
4. `capstone-exact-recipe.md` states `3/2:27/16`; the page shows
   `1..1/2:1..11/16`.

Usability (from code):

- The calculator page evaluates on the main thread with no Stop
  (`src/main.js:491,570`); a long computation freezes the tab. Tutorials already
  use a disposable worker.
- Bundles are unminified: 5.2 MB and 2.0 MB chunks, plus 11 MB of committed
  source maps.
- Tutorial edits and progress are lost on reload; only number settings persist.
- Tutorial text areas have no labels and output is not a live region.
- 73 of 89 challenges are an empty box with no hint, solution or check.
- Sandboxing looks sound: no fetch or import capability, `.js` modules refused,
  output HTML-escaped.

## 4. Legacy calculators (`apps/calc`, `apps/webcalc`)

Verified in the CLI:

1. **Any fraction with a decimal period over 30 cannot be shown in any mode.**
   `1/97` gives "Repeating decimal period is 96 digits, exceeding limit 30".
   The same error breaks `355/113`, `2^0.5`, and the help's own example.
2. **Whitespace is stripped before parsing:** `3 4` gives `34`, and `1 2/3`
   gives `4`.
3. **HELP documents syntax that fails:** every `1.2[3,6]`-style example errors
   because the separator is now `:`.
4. **One message, "Invalid rational number format", covers most mistakes**,
   including undefined variables and unknown functions.
5. Internal encodings leak: `x x` reports `z[10]3`; typing `P` prints
   `@x^0z[10]2`; `PI` after `LOAD reals` prints JavaScript source.
6. `LOAD scientific` reports its packages are not implemented; `2^3^2` is a
   parse error; `2.5e-2` fails while `2.5E-2` works.

Web calculator: the published `docs/calc.js` is older than its source (343 KB
against 549 KB rebuilt); `calc.html:16` has a stray `</edits>` tag; the mobile
keypad has no letters or `=`, so variables and functions are unreachable on a
phone; there are no ARIA attributes. `apps/quadratic/` is empty.

Given that RiX supersedes this system, the practical question is whether to fix
these or retire the calculators in favour of RiX Web. Items 1 and 2 are the only
ones I would fix regardless.

## 5. RiX notebook (`rix-nb`)

Verified by driving `rix-engine.js` headlessly (in-app behaviour is inferred):

1. **Four of five shipped example notebooks fail on the asynchronous path the
   hosts use**, hitting the default 2M-step or 30 s budget. The example test
   passes because it calls the unbudgeted synchronous path.
2. **A runaway recursive cell blocks the event loop for the whole time budget
   and then discards the entire run**, including earlier cells' results. At the
   default that is a 30 s freeze in a live-as-you-type editor.
3. **Static export hides errors.** A cell `x := 3; y := x/0; z := 5;` exports
   `3` with no sign of the failure.
4. **A trailing `##` comment corrupts result rows** and makes the exported
   output `_` instead of the value.
5. **Fence and inline scanning is not Markdown-aware.** A `rix` fence inside a
   four-backtick example is executed, and `@{...}` inside inline code is
   replaced.
6. The README lists an `expensive` mode that nothing reads; unknown fence tokens
   are collected and never reported.

State semantics for flow, singleton and refresh cells behave as documented, and
capability sandboxing held against every escape I tried.

## 6. Repository and documentation drift

- Root `AGENTS.md` gives the ternary as `x > 0 ?? x ?: -x`, which is now a parse
  error (the form is `cond ?: yes ?_ no`). It shows `f = x -> ...` with a
  lowercase call and `#` comments, both of which fail. It points to
  `rix/introduction.md`, `rix/rix-rationales.md` and `rix/parser/design/`, none
  of which exist; the files are under `rix/documentation/`. Since agents read
  this file first, it is worth fixing soon.
- `lang.md` uses the old `??`/`?:` ternary and `?|` parameter defaults.
- `rix/documentation/language-at-a-glance.qmd` contains
  `[1, |+ 1, |^ _][1:5]`, which fails with "Generator limit must be an integer
  or callable predicate". Its blocks are marked `parse=true`, so they are only
  parsed, never run. Switching that page to executed blocks would catch this.
- `rix-ed` is exercised by the umbrella test runner but is untracked, not a
  submodule.
- The umbrella root holds loose `demo*.rix`, `phase3.md` and
  `merger-analysis.md` from earlier phases.

## Suggested order of work

1. Chained comparisons, collection `==`, and mixed-type `<` (small evaluator and
   parser changes, high payoff).
2. Decide the `/` versus `~[...]` precedence and fix the two tutorial cells.
3. Raise or make configurable the 10,000-element sequence limit; add a
   recursion-depth error; fix core `pow`.
4. Make the tutorial test compare stated outputs, and add it to a regular
   profile.
5. Fix core `Integer` versus `Rational` comparison and the string constructor
   before the next core release.
6. Refresh `AGENTS.md` and `lang.md`.
7. Notebook: budget handling on the async path, and error visibility in export.
8. Decide the future of the legacy calculators.
